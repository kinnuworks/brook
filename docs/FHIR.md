# Brook and HL7 FHIR

Brook turns each citizen stream check into one HL7 FHIR R4 (4.0.1) **transaction Bundle**, shaped by the
OneAquaHealth FHIR Implementation Guide (**OAH IG**, package `hl7.eu.fhir.oah`, canonical
`http://hl7.eu/fhir/ig/oah`, source <https://github.com/hl7-eu/oah>), and forwards it to OneAquaHealth's
public FHIR sandbox. This page says how, what was validated, with which tools, and where the IG and Brook
do not yet fit. Everything here is reproducible with the commands at the end.

- Builder: [`src/core/fhir.ts`](../src/core/fhir.ts) (`buildBundle`)
- Brook's own definitions: [`public/fhir/`](../public/fhir/) (generated by [`scripts/fhir-definitions.mjs`](../scripts/fhir-definitions.mjs))
- Evidence: [`docs/evidence/`](evidence/) (sample bundles, validator outcomes, sandbox round trip)
- Tests: [`tests/fhir.test.ts`](../tests/fhir.test.ts)

returned that Observation (total 1). The sandbox accepting these resources is not, by itself, evidence of
profile conformance; the validator results above are.

## What a check becomes

One transaction Bundle (`meta.tag` `brook-citizen-check` on the Bundle and on every resource; the API only
forwards bundles where every resource carries it):

| Resource | Profile claimed | Content |
|---|---|---|
| `Location` | `location-oah`, always | The OAH research site (`identifier` system `https://api.enora-oah.eu/api/sites`, e.g. `O17`, id `oah-site-o17`) or a volunteer-added stream (`…/fhir/user-sites`); name, `mode` = instance, position |
| `QuestionnaireResponse` | none (answers Brook's Questionnaire) | The raw form, field for field, in native types; `subject` = the Location, `author` = the citizen's pseudonymous identifier |
| `Observation` × up to 6 | `observation-indicators-oah` **only once verified** | One per OAH indicator group (table below); one component per app field; `derivedFrom` the QuestionnaireResponse |
| `Observation` (overall) | same rule | The citizen's own assessment, `GOOD` / `MODERATE` / `POOR` |
| `Observation` (feelings) | none, ever | Joy, serenity, anger, fear, 0–5, as `valueInteger` components |
| `Device` `brook-app` | none | Brook, with its version |
| `Device` `brook-ai-<model>` | none | The AI model, only when one took part; one Device per model name |
| `Provenance` | none | Author = citizen, assembler = Brook, informant = the AI model (when used) |
| `Provenance` (verification) | none | Only once verified: verifier = the reviewer, `recorded` = when |

Every entry is `PUT <Type>/<id>` with ids derived deterministically (from the check's id, the site code, the
model name), so the offline queue can resend safely. `fullUrl`s are `https://brook-oah.vercel.app/fhir/<Type>/<id>`: identifiers in Brook's
namespace, consistent with each resource id, not endpoints Brook serves (Brook hosts definitions, not
instances). References inside the bundle are relative (`Location/oah-site-o17`), so they resolve within the
bundle and, after the PUTs, on the server.

### OneAquaHealth app field → OAH indicator → component

The codes of the Observations are the IG's own (`http://hl7.eu/fhir/ig/oah/CodeSystem/temporarySystem-oah-eu`,
including its spelling `morophology`). Component codes are the app's field names
(`https://brook-oah.vercel.app/fhir/CodeSystem/oah-citizen-fields`) and coded answers are the app's own values
(`…/CodeSystem/oah-citizen-answers`, `<field>.<value>`, displayed with OneAquaHealth's English label). The
grouping is Brook's; it is published as the ConceptMap
[`oah-citizen-fields-to-oah-indicators`](../public/fhir/ConceptMap-oah-citizen-fields-to-oah-indicators.json)
(`wider` everywhere except the three marked *relatedto*, which the IG has no closer indicator for).

| App field | Official question | OAH indicator | Component value |
|---|---|---|---|
| `channelForm` | The channel form is… | `morophology` | CodeableConcept: `channelForm.FLAT` `channelForm.U` `channelForm.V` |
| `bottomChannelType` | The bottom of the wet channel is… | `morophology` | CodeableConcept: `bottomChannelType.NAT` `bottomChannelType.ART` |
| `banksChannelType` | The banks of the channel are… | `morophology` | CodeableConcept: `banksChannelType.NAT` `banksChannelType.ART` `banksChannelType.LAS` |
| `habitats` | The habitats present are… | `morophology` | CodeableConcept, one component per ticked option: `habitats.SB` `.SI` `.SD` `.RF` `.AV`; none → OAH `absent` |
| `fallenBiomassTypes` | There are… | `morophology` | CodeableConcept, one component per ticked option: `fallenBiomassTypes.FT` `.FB` `.FL`; none → OAH `absent` |
| `waterFlow` | How is the water flowing? | `hydrology` | CodeableConcept: `waterFlow.FAS` `.NOR` `.STA` `.DRY` |
| `waterHeight` | What is the water height? (in metres) | `hydrology` | Quantity, UCUM `m` |

| `waterAbstraction` | Is there any kind of obvious water collection, use, removal from the stream? | `hydrology` | CodeableConcept: v2-0532 `Y` / `N` |
| `waterColor` | How is the water? | `foam` | CodeableConcept: `waterColor.CL` `.MU` `.FO` `.CO` |

| `construction` | Is there any construction/works in stream? | `foam` (relatedto) | CodeableConcept: v2-0532 `Y` / `N` |
| `imperviousAreasLeft` | Is more than one third of the left margin covered by impervious areas (such as roads, sidewalks or buildings)? | `LandUse` | CodeableConcept: v2-0532 `Y` / `N` |

| `overallAssessment` | Provide an overall assessment of the stream ecosystem health | own Observation, code `oah-citizen-fields#overallAssessment` | `valueCodeableConcept`: `overallAssessment.GOOD` `.MODERATE` `.POOR` |
| `joy` `serenity` `anger` `fear` | Which feeling(s) best describe your experience? | own Observation, code `oah-citizen-fields#feelings` | components `feelings.joy` … , `valueInteger` 0–5 |

"I'm not sure" (allowed for every field but the overall assessment, and stored as `null` by the app) becomes
a component valued `data-absent-reason#asked-unknown`, and the QuestionnaireResponse item is left unanswered.

Why these value types: `observation-indicators-oah` requires `Observation.component.value[x]` (min 1) and allows
only CodeableConcept, Quantity or string. So yes/no is coded (HL7 `v2-0532` `Y`/`N`, the code system behind
the HL7 `v2-0136` yes/no value set) rather than `valueBoolean`, counts are UCUM quantities rather than
`valueInteger`, and "not sure" is a coded value rather than `component.dataAbsentReason`. A multi-select is one
component per ticked option, because codings inside one CodeableConcept must all mean the same thing. The
representation is the same before and after verification, so verifying never changes an answer
(`tests/fhir.test.ts` pins this).

## Brook's definitions

Served from this app, so their canonical URLs resolve once deployed. Each is published twice from one object
by `scripts/fhir-definitions.mjs`: `public/fhir/<Type>-<id>.json` and `public/fhir/<Type>/<id>` (the canonical
path; `vercel.json` serves `/fhir/*` as `application/fhir+json` with CORS). `public/fhir/index.json` lists them
in the FHIR package `.index.json` shape. All are `status: draft`, `experimental: true`, version `0.1.0`,
publisher "Brook (hackathon prototype)", and none is an official OneAquaHealth artefact.

| Canonical (`https://brook-oah.vercel.app/fhir/…`) | What it holds |
|---|---|
| `CodeSystem/oah-citizen-fields` | The app's field names (+ `overallAssessment`, `feelings`, `feelings.joy/serenity/anger/fear`); definition = OAH's official question |
| `CodeSystem/oah-citizen-answers` | One code per coded answer, `<field>.<value>`, display = OAH's English label; properties `field`, `appValue` |
| `CodeSystem/tags` | `brook-citizen-check` |
| `CodeSystem/answer-source`, `ValueSet/answer-source` | `tap` `voice` `text` `voice-ai` `text-ai` `photo-confirmed` `photo-corrected` |
| `StructureDefinition/answer-source` | Extension (`valueCode`, required binding to the value set) on `Observation.component` and `Observation` |
| `Questionnaire/oah-citizen-check` | The check, item linkIds = field names, texts = OAH's official questions, `answerOption`s = the app's codes, `enableWhen` for the four follow-up questions, UCUM unit and min/max where the app has them |
| `ValueSet/oah-citizen-fields`, `ConceptMap/oah-citizen-fields-to-oah-indicators` | The field → indicator grouping above |

Displays come from `src/i18n/en.ts` (OneAquaHealth's official labels and Brook's short field names), so the
CodeSystems and the bundles cannot disagree; `tests/fhir.test.ts` fails when `public/fhir` is out of date.

## Preliminary → final, and why

`observation-indicators-oah` fixes `Observation.status` to `final` (`patternCode`) and makes `performer`
mandatory (and `subject` a `location-oah` Location, `effective[x]` mandatory). A citizen's report that nobody has
reviewed is not final in FHIR's sense, so Brook records it as `preliminary` and claims **no** Observation
profile. It is still valid FHIR R4 and valid against Brook's definitions (bundles a and c), and its Location
still claims `location-oah`. Claiming the profile with status `preliminary` is rejected by the validator
(`broken-3`).

When a researcher verifies a check (`verifiedBy`, `verifiedAt`), `buildBundle` returns the same content with:
`status: final`, the reviewer added to `performer` (R4 defines performer as who is responsible for asserting the
value), `meta.profile` = `observation-indicators-oah` on the indicator Observations (up to six) and the overall
assessment, and a second Provenance (`agent.type` = `verifier`, activity `v3-DataOperation#UPDATE`). The
citizen's own Provenance is unchanged. The feelings Observation becomes final too but never claims the profile:
they are not stream indicators.

This is a gap in the IG, not a choice Brook would make on its own: as published, the indicator profile has no
place for an unverified citizen observation. Options for OneAquaHealth: allow `preliminary` in
`observation-indicators-oah`, or add a citizen-science Observation profile derived from it with `status`
`preliminary | final`.

## AI transparency

- **Per answer.** Every component (and the overall-assessment Observation itself) carries the `answer-source`
  extension: `tap`; `voice` / `text` (matched by Brook's on-phone word lists, no AI); `voice-ai` / `text-ai` (the
  word lists could not place a free reply, so an AI model mapped it to one of the question's own codes, which the
  citizen was shown); `photo-confirmed` / `photo-corrected` (an AI model suggested an answer from the citizen's
  photo and the citizen gave the same / a different one).
- **Per resource.** Resources holding at least one value an AI asserted (`photo-confirmed`, `voice-ai`,
  `text-ai`) carry the HL7 security label `v3-ObservationValue#AIAST` ("Artificial Intelligence asserted"):
  the QuestionnaireResponse and the Observations concerned. `photo-corrected` does **not**: the recorded value is
  the citizen's, not the model's. Location, Devices and Provenance never carry it.
- **Per check.** The Provenance names the citizen (`author`), Brook (`assembler`, `Device/brook-app`) and, whenever
  a model took part, including suggestions the citizen corrected, the model (`informant`,
  `Device/brook-ai-<model>`). Each model name gets its own Device id, so a later check with another model can
  never change what an earlier Provenance points at.
- **Not in the bundle.** The photos, and the value a corrected AI suggestion had proposed. The bundle records that
  a suggestion was corrected, not what it was.

## Findings about the IG

1. **Unverified observations cannot conform** to `observation-indicators-oah` (status fixed to `final`, performer
   required). See above. Evidence: `broken-2`, `broken-3`.
2. **`location-oah`'s `referenceForm` slice is rejected by the validator.** It uses
   `http://hl7.org/fhir/StructureDefinition/artifact-relatedArtifact`, whose declared contexts (extension packages
   loaded by the validator: `hl7.fhir.uv.extensions` 5.3.0, `hl7.fhir.uv.extensions.r4` 5.2.0) do not include
   `Location`; the validator reports `Extension_EXTP_Context_Wrong_VER` (`gap-location-referenceForm.json`). The
   slice is optional (0..\*), so Brook leaves it out and links form and site through
   `QuestionnaireResponse.subject` → Location and `Observation.derivedFrom` → QuestionnaireResponse.
3. **The IG defines indicator-level codes only.** There are no codes for the citizen protocol's individual
   questions or answers, so component and answer codes are Brook's (`oah-citizen-fields`,
   `oah-citizen-answers`), taken verbatim from the OneAquaHealth app. The IG's *preferred* binding on
   `Observation.component.code` therefore yields one information-level note per component. The IG also has no
   indicator for pollution sources or works, so `pipes`, `waterDischarge` and `construction` sit under `foam`
   (marked `relatedto` in the ConceptMap).
4. **Building the IG.** SUSHI could not download `hl7.fhir.r4.core#4.0.1` and `hl7.fhir.uv.xver-r5.r4#0.1.0`
   from `packages.fhir.org` within its timeout here (slow registry, not an IG defect). Fetching both tarballs with
   `curl` into `~/.fhir/packages/<id>#<version>/` fixed it; SUSHI then reported 0 errors, 0 warnings.

## Limits

- Brook's definitions are drafts on a hackathon domain, not reviewed by OneAquaHealth or HL7. Validation is
  against the IG's current source (`0.1.0-ci-build`), not a published release.
- The citizen appears only as a pseudonymous identifier (`…/fhir/citizens`); the reviewer only as a display name.
  No Patient, Practitioner or RelatedPerson is created: none fits a citizen scientist, and Brook keeps no personal
  data.
- Displays and narratives are English (Brook speaks seven languages; the record uses OneAquaHealth's English
  wording). Narratives are short summaries generated from the data.
- Instances are sent to the OAH sandbox only; Brook does not run a FHIR server.

## Reproduce the validation

```bash
# 1. Build the OneAquaHealth IG from source (we used commit b907cf0)
git clone https://github.com/hl7-eu/oah.git
(cd oah && npx --yes fsh-sushi@3 --snapshot .)        # SUSHI 3.20.1 → oah/fsh-generated/resources
#    If SUSHI cannot download a package, fetch it into the cache, e.g.:
#    mkdir -p ~/.fhir/packages/hl7.fhir.r4.core#4.0.1 && curl -L https://packages.fhir.org/hl7.fhir.r4.core/4.0.1 | tar -xz -C ~/.fhir/packages/hl7.fhir.r4.core#4.0.1

# 2. The HL7 validator (we used 6.10.4; it needs Java, we used OpenJDK 27)
curl -L -o validator_cli.jar https://github.com/hapifhir/org.hl7.fhir.core/releases/latest/download/validator_cli.jar

# 3. In this repository: regenerate definitions and sample bundles, then validate them all
npx --yes tsx scripts/fhir-definitions.mjs      # → public/fhir/
npx --yes tsx scripts/fhir-samples.mjs          # → docs/evidence/bundles/
FHIR_VALIDATOR_JAR=$PWD/../validator_cli.jar OAH_IG_DIR=$PWD/../oah/fsh-generated/resources \
  node scripts/fhir-validate.mjs                # → docs/evidence/validation/ (exits 1 if any file surprises)

#    The same check by hand, for one bundle:
java -jar validator_cli.jar docs/evidence/bundles/b-verified-check-o17.json -version 4.0.1 \
  -ig ../oah/fsh-generated/resources -ig public/fhir -tx https://tx.fhir.org -check-display Check -show-message-ids

# 4. Unit tests, and the sandbox round trip (posts bundle b only)
npx vitest run tests/fhir.test.ts
node scripts/fhir-sandbox-roundtrip.mjs         # → docs/evidence/sandbox-roundtrip.json
```

Paths in step 3 assume the IG and the jar sit next to this repository; set `JAVA=/path/to/java` if `java` is not on
the `PATH`. The first validator run downloads its own packages (several minutes); later runs take seconds.
